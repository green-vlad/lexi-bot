# lexi-bot — план реализации

Telegram-бот для заучивания слов: выдаёт по N новых слов в день и ведёт интервальное
повторение в стиле Anki. Язык изучения и язык перевода выбирает пользователь —
жёстких пар (ko→ru и т.п.) в модели нет.

Статус документа: базовый проект архитектуры. Разбивка на исполняемые задачи —
в [TASKS.md](./TASKS.md).

---

## 1. Требования

### Функциональные

| # | Требование |
|---|---|
| F1 | Любая пара языков «изучаемый → язык перевода», выбирается пользователем |
| F2 | N новых слов в день (настраивается), лимит считается по календарным суткам в TZ пользователя |
| F3 | Интервальное повторение (SM-2, как в классическом Anki) |
| F4 | Три режима проверки: ввод текстом, выбор из 4 вариантов, «помню / не помню» |
| F5 | Встроенные частотные словари по языкам |
| F6 | Добавление своих слов по одному через UI бота |
| F7 | Импорт своих слов из CSV-файла |
| F8 | Интерфейс на русском и английском, расширяемый на другие языки |
| F9 | Напоминания в заданное пользователем время |
| F10 | Статистика: выучено, на повторении, серия дней, прогноз нагрузки |

### Нефункциональные

| # | Требование |
|---|---|
| N1 | ~100 одновременных пользователей (потолок на старте) |
| N2 | Чистая архитектура: домен не знает ни о Telegram, ни о СУБД |
| N3 | Высокое покрытие тестами: домен и use-case — юнит-тестами, репозитории — интеграционными |
| N4 | Go 1.25 |

### Принятые за нас решения (можно пересмотреть)

* **SRS-алгоритм — SM-2.** Детерминированный, полностью покрывается табличными тестами.
  Спрятан за интерфейсом `study.Scheduler`, так что FSRS добавляется второй реализацией
  без изменения use-case'ов.
* **Транспорт — long polling.** Не требует публичного HTTPS-домена, на 100 пользователей
  с огромным запасом. Спрятан за `port.BotTransport`; webhook — альтернативная реализация.

## 2. Выбор хранилища: PostgreSQL

Берём реляционную БД, а не MongoDB. Обоснование:

1. **Данные строго реляционные.** Пользователь → курс → карточка → лексема → переводы →
   журнал повторений. Это граф связей, а не документы. В Mongo пришлось бы либо дублировать
   лексемы в каждую карточку, либо всё равно делать «джойны» руками в коде.
2. **Главный запрос — диапазонный по времени.** «Взять карточки пользователя с `due_at <= now`,
   отсортировать, взять первые K» — это ровно то, для чего существует B-tree индекс по
   `(user_course_id, due_at)`. Postgres делает это index-only-scan'ом.
3. **Нужны транзакции.** Выдача новых слов и запись ответа — это несколько
   согласованных изменений (`cards` + `reviews` + счётчик дневного лимита). В одной
   транзакции это тривиально и безопасно при повторных нажатиях кнопок.
4. **Аналитика без вычислительного оверхеда.** Статистика и прогноз нагрузки — обычные
   агрегаты `GROUP BY`, а не aggregation pipeline.
5. **Нагрузка не является аргументом.** 100 конкурентных пользователей — это единицы
   запросов в секунду. Обе СУБД справятся, поэтому решает модель данных, а она реляционная.

Драйвер — `pgx/v5` напрямую (`pgxpool`), без ORM. Запросы пишем руками: их немного,
они предсказуемы, и SQL остаётся видимым. Миграции — `goose` (обычные `.sql`-файлы,
встроенные через `embed.FS`, применяются при старте).

## 3. Архитектура

### Правило зависимостей

```
        infra  ─────┐
                    ▼
adapter ─────► usecase ─────► domain
(telegram,     (сценарии,     (сущности,
 postgres,      порты)         SM-2,
 i18n, csv)                    правила)
```

Стрелка = «знает о». `domain` не импортирует ничего из проекта и почти ничего из
стандартной библиотеки (только `time`, `errors`). `usecase` объявляет **порты**
(интерфейсы репозиториев и внешних сервисов) — реализации живут в `adapter`.
Сборка графа зависимостей — вручную в `cmd/bot/main.go`, без DI-фреймворка.

### Структура каталогов

```
lexi-bot/
├── cmd/
│   ├── bot/main.go            # точка входа: конфиг → пул → репо → usecase → telegram
│   └── seeder/main.go         # загрузка встроенных словарей в БД
├── internal/
│   ├── domain/                # ← нет внешних зависимостей
│   │   ├── user/              # User, UILang, Timezone, Settings
│   │   ├── lexicon/           # Language, Lexeme, Translation, Deck
│   │   └── study/             # Card, CardState, Rating, Review, Scheduler + SM-2
│   ├── usecase/
│   │   ├── port/              # интерфейсы: репозитории, Messenger, Clock, Translator
│   │   ├── onboarding/        # регистрация, выбор языков и колоды
│   │   ├── session/           # учебная сессия: выдача карточек и приём ответов
```

### Ключевые доменные типы (эскиз)

```go
// domain/study
type Rating uint8 // Again=1, Hard=2, Good=3, Easy=4

type State uint8  // New, Learning, Review, Relearning, Suspended

type CardState struct {
    State        State
    DueAt        time.Time
    IntervalDays float64
    EaseFactor   float64 // SM-2 EF, минимум 1.3
    Repetitions  int
    Lapses       int
    LearnStep    int     // индекс в learning steps
}

// Чистая функция: (состояние, оценка, момент времени) → новое состояние.
// Никаких обращений к БД, времени «изнутри» и рандома — идеальна для табличных тестов.
type Scheduler interface {
    Next(cur CardState, r Rating, now time.Time) CardState
}
```

## 4. Модель данных

Ключевое решение: **лексема хранится один раз, переводы — отдельной таблицей на N языков.**
Это то, что даёт «любой язык с любого»: один корейский частотный список обслуживает
и корейский→русский, и корейский→английский; добавление нового языка перевода — это
вставка строк в `translations`, а не новая колода.

```
languages ──┐
            ├──< lexemes ──< translations
decks ──< deck_items >──┘        │
  │                              │
users ──< user_courses ──< cards ┘──< reviews
  ├──< user_sessions (FSM)
  └──< import_jobs
```

### Таблицы

**`languages`** — `code` (PK, BCP-47: `ko`, `en`, `ru`, `pt-BR`), `name_native`, `has_reading`
(нужна ли транскрипция), `is_ui` (доступен ли как язык интерфейса).

**`lexemes`** — слово изучаемого языка.
`id`, `lang_code`, `term`, `reading` (транскрипция/ромадзи, nullable), `pos` (часть речи),
`freq_rank`, `owner_user_id` (NULL = встроенное, иначе личное слово пользователя), `created_at`.
Уникальность: `(lang_code, term, pos, coalesce(owner_user_id, 0))`.

**`translations`** — `id`, `lexeme_id`, `lang_code`, `text`, `is_primary`, `note`.
Индекс `(lexeme_id, lang_code)`. Несколько строк на язык = несколько допустимых значений
(важно для режима ввода текстом: засчитываем любой вариант).

**`decks`** — `id`, `code` (уникальный слаг для встроенных: `ko-top-2000`), `owner_user_id`
(NULL = встроенная), `lang_code` (язык изучения), `title`, `description`, `size`, `is_builtin`.

**`deck_items`** — `deck_id`, `lexeme_id`, `position` (порядок выдачи; для встроенных = по
частотности). PK `(deck_id, lexeme_id)`, индекс `(deck_id, position)`.

**`users`** — `id`, `tg_user_id` (UNIQUE), `tg_username`, `ui_lang`,
`created_at`, `deleted_at`.

**`user_settings`** — `user_id` (PK), `new_per_day`, `max_reviews_per_day`, `reminder_at`
(local time, nullable = выключено), `timezone` (IANA), `quiz_modes` (массив включённых
режимов), `reverse_direction` (перевод→слово).

Таймзона лежит рядом с дневными лимитами, а не в `users`, потому что нужна ровно им:
она задаёт границу суток, по которой лимиты обнуляются. В домене она по той же причине
живёт в `user.Settings`, и схема повторяет это один в один.

**`user_courses`** — «пользователь учит колоду X с переводом на язык Y».
`id`, `user_id`, `deck_id`, `translation_lang`, `status` (active/paused/archived), `created_at`.
UNIQUE `(user_id, deck_id, translation_lang)`.

**`cards`** — состояние SRS. `id`, `user_course_id`, `lexeme_id`, `state`, `due_at`,
`interval_days`, `ease_factor`, `repetitions`, `lapses`, `learn_step`,
`introduced_at`, `last_reviewed_at`. UNIQUE `(user_course_id, lexeme_id)`.
Главный индекс: `(user_course_id, due_at) WHERE state <> 'suspended'`.

**`reviews`** — журнал, только вставки. `id`, `card_id`, `user_id`, `rated_at`, `rating`,
`mode` (typing/choice/recall), `answer_raw`, `is_correct`, `duration_ms`,
`prev_interval`, `new_interval`, `prev_ef`, `new_ef`.
Нужен для статистики и как обучающая выборка, если позже подключим FSRS.

**`daily_counters`** — `user_course_id`, `day` (дата в TZ пользователя), `new_introduced`,
`reviews_done`. PK `(user_course_id, day)`. Считать лимит из `cards.introduced_at`
теоретически можно, но отдельный счётчик делает проверку лимита одной дешёвой строкой
и корректно работает при смене таймзоны.

**`user_sessions`** — состояние диалога (FSM): `user_id` (PK), `state`, `payload` (jsonb),
`updated_at`. В БД, а не в памяти: переживает рестарт, при 100 пользователях цена нулевая.

**`import_jobs`** — `id`, `user_id`, `file_name`, `status`, `rows_total`, `rows_imported`,
`rows_failed`, `error_report` (jsonb), `created_at`.

**`outbox_notifications`** — `id`, `user_id`, `kind`, `scheduled_for`, `sent_at`, `payload`.
Гарантирует, что напоминание не уйдёт дважды при рестарте или двух инстансах.

## 5. Учебная сессия

### Порядок выдачи

1. Просроченные повторения (`due_at <= now`), сортировка по `due_at`, до `max_reviews_per_day`.
2. Карточки в фазе обучения, у которых подошёл шаг.
3. Новые слова — из `deck_items` по `position`, но не больше остатка дневного лимита
   (`new_per_day - daily_counters.new_introduced`).

Дневная граница — полночь в таймзоне пользователя, а не UTC.

### Режимы проверки и отображение в оценку SM-2

| Режим | Что видит пользователь | Отображение результата |
|---|---|---|
| `recall` | Слово → «Показать перевод» → кнопки оценки | Кнопки напрямую: Again / Hard / Good / Easy |
| `choice` | Слово + 4 кнопки-варианта | верно → `Good`; верно и быстро (< 3 c) → `Easy`; неверно → `Again` |
| `typing` | Слово + приглашение напечатать перевод | точное совпадение → `Good`; совпадение после нормализации или опечатка (расстояние Левенштейна ≤ 1) → `Hard`; иначе → `Again` |

Режимы включаются в настройках; если включено несколько — бот чередует их
детерминированно (по хешу `card_id + repetitions`), чтобы поведение было воспроизводимо в тестах.

**Нормализация ответа при вводе:** Unicode NFC → нижний регистр → схлопывание пробелов →
отсечение артиклей и `to ` у глаголов (правила зависят от языка перевода, лежат в
`domain/lexicon`) → сравнение со **всеми** переводами лексемы, а не только с primary.

**Дистракторы для режима выбора:** 3 случайных перевода из той же колоды, по возможности
той же части речи, с исключением совпадающих с правильным ответом (в том числе после
нормализации). Источник случайности — инжектируемый интерфейс, чтобы тесты были детерминированы.

### Идемпотентность

Callback-кнопки в Telegram легко нажать дважды. Каждая карточка выдаётся с токеном
попытки (`attempt_id` в `callback_data`); повторный ответ с тем же токеном не создаёт
второй `review` и не двигает `due_at` — бот просто отвечает на callback без изменений.

## 6. Telegram-слой

Библиотека — `github.com/go-telegram/bot`: контекстная, без транзитивных зависимостей,
активно поддерживается. Обёрнута в собственный интерфейс `port.Messenger`
(`SendMessage`, `EditMessage`, `AnswerCallback`, `DownloadFile`), поэтому хендлеры
тестируются на фейке, а замена библиотеки затрагивает один файл.

### Команды

| Команда | Назначение |
|---|---|
| `/start` | Онбординг: язык интерфейса → язык изучения → язык перевода → колода → слов в день → таймзона и время напоминания |
| `/learn` | Учебная сессия |
| `/add` | Добавить своё слово |
| `/import` | Импорт CSV (бот ждёт файл) |
| `/decks` | Мои курсы: переключение, пауза, добавление нового |
| `/settings` | Настройки |
| `/stats` | Статистика |
| `/help`, `/language`, `/delete_me` | Справка, смена языка интерфейса, удаление данных |

### Ограничения платформы, которые закладываем сразу

* `callback_data` ≤ 64 байт → компактный формат `«действие:id:параметр»`, без JSON.
* На каждый callback обязателен `answerCallbackQuery`, иначе у пользователя висит «часики».
* Лимиты отправки: ~1 сообщение/с в один чат, ~30/с суммарно → рассылка напоминаний
  идёт через ограничитель скорости (`golang.org/x/time/rate`).
* Файлы бот скачивает через `getFile` — размер ограничен 20 МБ, для CSV ставим свой
  лимит 2 МБ и 5000 строк.

## 7. Локализация

`nicksnyder/go-i18n/v2`, каталоги `locales/*.toml`, встроенные через `embed.FS`.
Множественные формы обязательны — в русском их три («1 слово / 2 слова / 5 слов»),
самописный `map[string]string` тут не годится.

Тексты в хендлеры попадают только через `port.Localizer`; строковых литералов
на русском/английском в коде нет. Отдельный тест проходит по всем локалям и падает,
если в какой-то из них не хватает ключа или не совпадает набор плейсхолдеров —
благодаря этому добавление третьего языка не требует ревизии кода.

Отдельно локализуются: язык интерфейса (`users.ui_lang`) и язык перевода карточек
(`user_courses.translation_lang`) — это разные вещи, их нельзя смешивать.

## 8. Встроенные словари

Формат сида — по файлу на язык изучения плюс файлы переводов:

```
seeds/
├── decks.yaml               # метаданные колод: код, язык, название, описание
├── lexemes/ko.jsonl         # {"term":"사람","reading":"saram","pos":"noun","rank":12}
└── translations/ko-ru.jsonl # {"term":"사람","pos":"noun","texts":["человек","люди"]}
```

`cmd/seeder` идемпотентен: повторный запуск обновляет изменившееся и не плодит дубли
(`INSERT ... ON CONFLICT DO UPDATE`). Это позволяет докидывать новые языки перевода к уже
существующим лексемам без пересборки колод.

На старте: корейский, английский, испанский (топ-2000 частотных) с переводами на ru и en.
Источники — открытые частотные списки и Wiktionary-выгрузки; лицензии фиксируем
в `seeds/SOURCES.md`.

## 9. Пользовательские слова

**По одному (`/add`):** диалог просит слово → перевод → (опционально) транскрипцию и пример.
Слово попадает в личную колоду `«Мои слова: <язык>»`, создаваемую при первом добавлении.
Если такая лексема уже есть во встроенном словаре — предлагаем добавить существующую
карточку вместо дубликата.

**CSV (`/import`):** UTF-8 (с BOM или без), разделитель `,` или `;` (определяется
автоматически), заголовок обязателен:

```csv
term,translation,reading,pos,example
사람,человек;люди,saram,noun,좋은 사람입니다
```

Несколько переводов — через `;`. Импорт построчный и частичный: корректные строки
загружаются, ошибочные попадают в отчёт с номером строки и причиной, пользователю
приходит сводка «загружено 412, пропущено 8» и файл с ошибками.

## 10. Напоминания и фоновые задачи

In-process планировщик (`robfig/cron/v3`), тик раз в 5 минут:

1. Выбрать пользователей, у которых локальное время совпало с `reminder_at`
   и на сегодня ещё нет записи в `outbox_notifications`.
2. Вставить строки в outbox в транзакции (это и есть защита от дублей).
3. Воркер-пул забирает неотправленные и шлёт через ограничитель скорости.

При запуске нескольких инстансов от одновременной обработки защищает
`pg_try_advisory_lock` на планировщике. Для 100 пользователей достаточно одного инстанса,
но конструкция сразу корректна.

## 11. Тестирование

| Слой | Как тестируем | Ориентир по покрытию |
|---|---|---|
| `domain` | Чистые табличные юнит-тесты. SM-2 — с зафиксированными эталонными последовательностями оценок | 95%+ |
| `usecase` | Юнит-тесты на фейковых портах (пишем руками, in-memory), инжектируемые `Clock` и `Rand` | 85%+ |
| `adapter/storage` | Интеграционные на реальном Postgres через `testcontainers-go`, тег `//go:build integration` | основные пути |
| `adapter/telegram` | Хендлеры на фейковом `Messenger`: проверяем текст, клавиатуру, переходы FSM | 80%+ |
| e2e | Фейковый Telegram Bot API на `httptest` + контейнер с БД: онбординг → сессия → ответ → сдвиг `due_at` | ключевые сценарии |

Правила, которые делают это возможным: время только через `port.Clock`, случайность только
через `port.Rand`, никаких глобальных переменных и `init()`-магии, хендлеры не создают
зависимости сами — получают в конструкторе.

CI (GitHub Actions): `golangci-lint` → `go test -race ./...` → интеграционные тесты
с сервисом Postgres → сборка Docker-образа.

## 12. Эксплуатация

Подробности — в [DEPLOY.md](./DEPLOY.md): сравнение площадок, GitHub Actions, бэкапы, мониторинг.
Кратко: VPS + Postgres в Docker Compose на том же хосте, образ из GHCR, деплой по SSH
из Actions после прохождения линта и тестов.


* Конфигурация из переменных окружения (`BOT_TOKEN`, `DATABASE_URL`, `LOG_LEVEL`, …),
  токен нигде не логируется.
* `docker-compose.yml`: бот + Postgres + том для данных.
* Логи — `log/slog` в JSON, в каждой записи `user_id` и `update_id` для трассировки.
* `/healthz` на отдельном порту: проверка пула БД и последнего успешного polling-цикла.
* Graceful shutdown: перестаём забирать апдейты, дорабатываем текущие, закрываем пул.
* Метрики Prometheus (`/metrics`): апдейты, ответы по режимам, задержки БД, ошибки Telegram API.
* Бэкап: `pg_dump` по cron, инструкция по восстановлению в `docs/RUNBOOK.md`.

## 13. Границы первой версии

Сознательно **не** делаем сейчас:

* FSRS (интерфейс готов, реализация позже);
* аудио и картинки на карточках;
* социальные функции (общие колоды между пользователями, рейтинги);
* веб-интерфейс и мультиинстансовое горизонтальное масштабирование;
* автоматический перевод через внешний API.

Каждый пункт помещается в существующую архитектуру без её перестройки — это и есть
основная проверка того, что границы слоёв проведены верно.
